# Agent Mesh Protocol — v2 Phase 1

Concise spec for the Phase 1 core engine. One node serves many agents;
node-to-node transport is Phase 4 and out of scope here.

## 1. Agent identity

An agent registers once (admin-only, see §5) and receives:

| Field | Meaning |
|---|---|
| `id` | Opaque id, `agt_` + 16 hex chars, generated by the node |
| `name` | Human display name (not unique, not an identifier) |
| `machine` / `node` | Where the agent runs |
| `capabilities` | List of strings, e.g. `["coding", "browser", "amharic"]` |
| `role` | `owner` \| `orchestrator` \| `worker` |
| `status` | `online` \| `busy` \| `offline` (default `online`) |
| `last_seen` | Updated by registration and `POST /agents/heartbeat` |
| auth token | `secrets.token_urlsafe(32)`, shown **once** at registration. The node stores only its SHA-256 hash. Sent as `Authorization: Bearer <token>` on every agent call. Missing/wrong token = `401`. |

Ordering rule (default matrix): owner may order anyone; orchestrator may
order workers; workers may report/ask but not order other workers. Phase 1
records roles; hard enforcement of the ordering matrix on task creation is
deferred (task creation is authenticated, assignee is recorded).

## 2. Messages

Reuses the v1 bus. Types stay free-form strings; conventional values:
`INFO`, `QUESTION`, `ANSWER`, `HANDOVER_OFFER`. A message has `sender`
(always the authenticated agent — a body-supplied sender is ignored),
`recipient` (agent id), `msg_type`, `payload` (string or JSON), optional
`correlation_id`. Delivery state in Phase 1: stored / unread, then
acknowledged via the v1 bus semantics.

## 3. Tasks

Fields: `id`, `title`, `instructions`, `requester` (agent id),
`assignee_agent` (agent id **or null**), `assignee_capability` (string
**or null**) — exactly one assignment style per task; `priority`
(`low|normal|high|urgent`, default `normal`); optional budgets
`budget_time_sec`, `budget_tokens`, `budget_money`; `parent_id` (subtask
link, informational); `depends_on` (task id that must be `DONE` first);
`idempotency_key`; `progress_notes` (append-only list of
`{agent, note, at}`); `result` (set on DONE/FAILED); timestamps.

Lifecycle — only these transitions are allowed; anything else is rejected
with `400` and a message naming the from/to states:

```
DRAFT      -> SENT
SENT       -> ACCEPTED | REJECTED
ACCEPTED   -> IN_PROGRESS
IN_PROGRESS-> IN_REVIEW | FAILED
IN_REVIEW  -> DONE | FAILED | IN_PROGRESS   (IN_PROGRESS = rework)
REJECTED, DONE, FAILED are terminal.
```

Dependency rule: a task with `depends_on` set cannot move to `ACCEPTED`
or `IN_PROGRESS` until the dependency task is `DONE`.

Idempotency: `POST /tasks` with an `idempotency_key` that already exists
returns the existing task (`200`, `duplicate: true`) and creates nothing.

## 4. Vault and broker permission model

Credentials live in the node's vault, encrypted at rest (see README:
Fernet when `cryptography` is installed, otherwise OpenSSL AES-256-CBC
encrypt-then-MAC; PBKDF2-HMAC-SHA256, per-store salt, master passphrase
from `AGENT_MESH_MASTER` or a `0600` key file). Plaintext secrets are
never written to disk, logs, audit entries, or any API response — API
listings show only service name, upstream, ACL and `has_secret: true`.

Per-service ACL: `acl = {agent_id: ["read"|"write"|"spend", ...]}` plus a
service-level `requires_approval` flag. A use-check
(`POST /vault/use-check {service, action}`) returns exactly one outcome:

- `deny` (`403`) — service unknown, agent not in ACL, or action not allowed.
- `needs_approval` (`200`) — agent and action are allowed, but the service
  has `requires_approval: true`; the broker must park the request for the
  owner. Phase 1 returns the decision; the approval queue UI is later.
- `allow` (`200`) — allowed, no approval needed.

Every use-check writes a sanitised audit line
(`{ts, agent, service, action, outcome}`) to `audit.log` in the data dir.
The raw secret is only ever decrypted inside the node process by the
broker path (`Vault.get_secret`, never exposed over HTTP).

## 5. Node API and auth

Base: `http://127.0.0.1:<port>` (default port 8790). JSON in/out.

| Route | Auth | Notes |
|---|---|---|
| `GET /health` | none | `{status: "ok"}` |
| `POST /agents/register` | admin | returns agent + one-time token |
| `POST /agents/heartbeat` | agent | body may set `status` |
| `GET /agents` | agent or admin | token hashes never returned |
| `POST /messages`, `GET /messages?recipient=` | agent | recipient defaults to caller |
| `POST /tasks`, `GET /tasks`, `GET /tasks/{id}` | agent | requester = caller |
| `POST /tasks/{id}/transition` `{to, result?}` | agent | §3 rules enforced |
| `POST /tasks/{id}/progress` `{note}` | agent | append-only |
| `POST /vault/services` | admin | secret in body only, never logged |
| `GET /vault/services` | agent or admin | safe listing, no secret material |
| `POST /vault/use-check` | agent | §4 outcomes |

Admin auth: `X-Admin-Token: <AGENT_MESH_ADMIN>`. Agent auth: Bearer token.
No/unknown credentials = `401`; authenticated but not permitted = `403`.
