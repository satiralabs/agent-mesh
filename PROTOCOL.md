# Agent Mesh Protocol — v2.0

Concise spec for the v2 engine (Phases 1-5). One node serves many
agents; paired nodes federate (§6).

## 1. Agent identity

An agent registers once (admin-only, see §5) and receives:

| Field | Meaning |
|---|---|
| `id` | Opaque id, `agt_` + 16 hex chars, generated by the node |
| `name` | Human display name (not unique, not an identifier) |
| `machine` / `node` | Where the agent runs |
| `capabilities` | List of strings, e.g. `["coding", "browser", "amharic"]` |
| `role` | `owner` \| `orchestrator` \| `worker` |
| `status` | `online` \| `busy` \| `offline` (default `online`) |
| `last_seen` | Updated by registration and `POST /agents/heartbeat` |
| auth token | `secrets.token_urlsafe(32)`, shown **once** at registration. The node stores only its SHA-256 hash. Sent as `Authorization: Bearer <token>` on every agent call. Missing/wrong token = `401`. |

**Ordering matrix (hard-enforced since Phase 5)** on every task
creation, local and remote-originated alike. A violation is rejected
with `403` and a reason naming the ids and roles involved, and the
denial is written to the audit log (`task_order_denied`):

- `owner` (an owner-role agent, or the reserved GUI actor `owner`):
  may order anyone — a named agent, or by capability.
- `orchestrator`: may order workers and orchestrators, named or by
  capability; may NOT order an owner-role agent.
- `worker`: may NOT create tasks for other agents at all. It may
  create a task assigned to itself, and it may send messages/questions
  to anyone — messages are not orders and are never matrix-checked.
- Capability-assigned tasks: only owner / orchestrator may create them.
- Remote-originated tasks (§6): the receiving node applies the same
  matrix using the requester's role from the sender's synced directory
  (the origin node's `owner` actor keeps owner rights). A requester
  who is not in the synced directory is denied — directory sync
  precedes task sync in the outbox, and a denial makes the sender's
  outbox retry rather than deliver. State merges for tasks that
  already exist on both sides are not creations and are not checked.

Default role: registration **without** an explicit role yields
`orchestrator`. Rationale (least surprise): Phases 1-4 recorded roles
without enforcing them, so agents registered role-less must keep
working exactly as before; the matrix bites as soon as an agent is
explicitly registered as a `worker` (or an orchestrator tries to order
an owner).

## 2. Messages

Reuses the v1 bus. Types stay free-form strings; conventional values:
`INFO`, `QUESTION`, `ANSWER`, `HANDOVER_OFFER`. A message has `sender`
(always the authenticated agent — a body-supplied sender is ignored),
`recipient` (agent id), `msg_type`, `payload` (string or JSON), optional
`correlation_id`. Delivery state in Phase 1: stored / unread, then
acknowledged via the v1 bus semantics.

## 3. Tasks

Fields: `id`, `title`, `instructions`, `requester` (agent id),
`assignee_agent` (agent id **or null**), `assignee_capability` (string
**or null**) — exactly one assignment style per task; `priority`
(`low|normal|high|urgent`, default `normal`); optional budgets
`budget_time_sec`, `budget_tokens`, `budget_money`; `parent_id` (subtask
link, informational); `depends_on` (task id that must be `DONE` first);
`idempotency_key`; `progress_notes` (append-only list of
`{agent, note, at}`); `result` (set on DONE/FAILED); timestamps.

Lifecycle — only these transitions are allowed; anything else is rejected
with `400` and a message naming the from/to states:

```
DRAFT      -> SENT
SENT       -> ACCEPTED | REJECTED
ACCEPTED   -> IN_PROGRESS
IN_PROGRESS-> IN_REVIEW | FAILED
IN_REVIEW  -> DONE | FAILED | IN_PROGRESS   (IN_PROGRESS = rework)
REJECTED, DONE, FAILED are terminal.
```

Dependency rule: a task with `depends_on` set cannot move to `ACCEPTED`
or `IN_PROGRESS` until the dependency task is `DONE`.

Idempotency: `POST /tasks` with an `idempotency_key` that already exists
returns the existing task (`200`, `duplicate: true`) and creates nothing.

## 4. Vault and broker permission model

Credentials live in the node's vault, encrypted at rest (see README:
Fernet when `cryptography` is installed, otherwise OpenSSL AES-256-CBC
encrypt-then-MAC; PBKDF2-HMAC-SHA256, per-store salt, master passphrase
from `AGENT_MESH_MASTER` or a `0600` key file). Plaintext secrets are
never written to disk, logs, audit entries, or any API response — API
listings show only service name, upstream, ACL and `has_secret: true`.

Per-service ACL: `acl = {agent_id: ["read"|"write"|"spend", ...]}` plus a
service-level `requires_approval` flag. A use-check
(`POST /vault/use-check {service, action}`) returns exactly one outcome:

- `deny` (`403`) — service unknown, agent not in ACL, or action not allowed.
- `needs_approval` (`200`) — agent and action are allowed, but the service
  has `requires_approval: true`; the broker must park the request for the
  owner. Phase 1 returns the decision; the approval queue UI is later.
- `allow` (`200`) — allowed, no approval needed.

Every use-check writes a sanitised audit line
(`{ts, agent, service, action, outcome}`) to `audit.log` in the data dir.
The raw secret is only ever decrypted inside the node process by the
broker path (`Vault.get_secret`, never exposed over HTTP).

## 4b. Secret scanner (Phase 5)

Outgoing content is scanned for credential shapes **before** it is
stored or forwarded: message payloads, task title / instructions /
result, progress notes, file-drop payloads, and peer-originated
messages / task snapshots on receipt. Rules (`agent_mesh/scan.py`):
PEM private-key blocks; token prefixes (`ghp_`/`gho_`…, `sk-…`,
`AKIA…`, `xox…-`, `Bearer <long>`, JWT-shaped); and
`password|api_key|secret|token = <value>` assignments whose value is
not an obvious placeholder (`YOUR_…`, `<…>`, `${…}`, `xxx`, `***`,
`changeme`, `example`, `redacted`, …). Plain prose mentioning those
words does not match.

On a hit the submission is rejected with `400` naming **only the
rule** — the matched text never appears in the error, the audit log,
or any response — and the block is audited (`secret_scan_blocked`,
rule + actor only). The owner (admin actor, or an owner-role agent)
may resend the same content with `allow_secret_risk: true`; the
override is audited (`secret_scan_override`). Non-owners who attempt
the override get `403`. File-drop has no override path: a blocked file
lands in `failed/` with the rule named in its `.error.txt`.

## 5. Node API and auth

Base: `http://127.0.0.1:<port>` (default port 8790). JSON in/out.

| Route | Auth | Notes |
|---|---|---|
| `GET /health` | none | `{status: "ok"}` |
| `POST /agents/register` | admin | returns agent + one-time token |
| `POST /agents/heartbeat` | agent | body may set `status` |
| `GET /agents` | agent or admin | token hashes never returned |
| `POST /messages`, `GET /messages?recipient=` | agent | recipient defaults to caller |
| `POST /tasks`, `GET /tasks`, `GET /tasks/{id}` | agent | requester = caller |
| `POST /tasks/{id}/transition` `{to, result?}` | agent | §3 rules enforced |
| `POST /tasks/{id}/progress` `{note}` | agent | append-only |
| `POST /vault/services` | admin | secret in body only, never logged |
| `GET /vault/services` | agent or admin | safe listing, no secret material |
| `POST /vault/use-check` | agent | §4 outcomes |

Admin auth: `X-Admin-Token: <AGENT_MESH_ADMIN>`. Agent auth: Bearer token.
No/unknown credentials = `401`; authenticated but not permitted = `403`.
`POST /tasks` additionally enforces the §1 ordering matrix (`403`) and
the §4b scanner (`400`); `POST /messages` enforces the §4b scanner, and
`GET /messages` returns only the caller's own inbox unless the caller
is the admin/owner.

## 6. Federation (Phase 4)

Each node has a persistent identity: `node_id` (`nod_` + 16 hex) and a
display name, stored in `<data dir>/node.json`.

**Pairing.** An admin on node B creates a pairing code
(`POST /peers/pairing-code`, admin): 8 hex chars, stored hashed, one
use, expires in ≤15 min (`AGENT_MESH_PAIR_TTL_SEC`). An admin on node A
calls `POST /peers/pair {peer_url, code}` on **A**; A then calls B's
`POST /peer/pair` with `{node_id, name, url, code}` — the code is that
call's only credential. On success B generates a per-peer secret
(`token_urlsafe(32)`) and returns it once in the pairing response; both
nodes store it in their own `peers.db` (0600). It is never logged and
never appears in any list/info response (`GET /peers` shows id, name,
url, status, timestamps only). Reusing the code, or a wrong/expired
code, fails. Pairing must happen over a trusted channel (LAN/Tailscale)
because the secret crosses in that one response.

**Signed transport.** All other `/peer/*` calls carry headers
`X-Mesh-Node` (sender node id), `X-Mesh-Timestamp` (unix seconds),
`X-Mesh-Signature` = hex HMAC-SHA256(peer_secret,
`timestamp + "." + METHOD + "." + path + "." + raw_body`). Receivers
reject unknown nodes (`403`), timestamps more than 5 minutes old
(`401`), and bad signatures (`401`). Peer credentials authorise
`/peer/*` only — they never satisfy agent or admin auth, and agent /
admin credentials never satisfy peer auth. HMAC provides
authentication + integrity, not confidentiality.

**Federation payloads** (all delivered via the outbox, below):
- `POST /peer/directory {node_id, name, agents}` — sender's local agent
  list; the receiver caches it as remote agents (`remote: true`,
  `home_node` = sender) and merges them into `GET /agents`.
- `POST /peer/task_sync {task}` — a full task snapshot. If the
  snapshot's `origin_node` is the receiver, it merges into the local
  task named by `origin_task_id`; otherwise the receiver upserts its
  home-side copy keyed by (`origin_node` = sender, `origin_task_id` =
  snapshot `id`). Merging is monotonic: status rank never moves
  backwards (a terminal state wins), progress notes union, a set result
  wins — so re-delivery and out-of-order delivery are harmless.
- `POST /peer/message {message}` — stored in the receiver's bus;
  duplicates are dropped by the message's stable `correlation_id`.

A task created for a remote agent is stored on the origin node with
`home_node` set; the home node's copy carries `origin_node` +
`origin_task_id`. Status changes, progress notes and results made on
either side queue a `task_sync` to the other side.

**Outbox.** All outbound peer deliveries are rows in `peers.db`:
`{peer, kind, payload, dedupe_key (unique per peer), state
(pending|delivered|failed), attempts, next_retry}`. A background loop
flushes due items in insertion order; backoff follows
`AGENT_MESH_RETRY_SCHEDULE` (default `1,5,15,60` seconds), flush
interval `AGENT_MESH_FLUSH_SEC` (default 2s); after
`AGENT_MESH_OUTBOX_MAX_ATTEMPTS` (default 100) an item is `failed`.
`POST /peers/flush` (admin) forces a pass; `GET /peers/outbox` (admin)
shows counts and recent items (payloads excluded). Meshes are
pairwise — no relaying through third nodes.
